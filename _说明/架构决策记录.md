本文件记录重要方案的原因、备选方案、代价与适用边界。强制规则集中见[开发规范](开发规范.md)，当前文件职责见[文件功能说明](文件功能说明.md)。

以下两项于 **2026-10-30 按现状补录**，代码基准为提交 `966b8b7`。它们不是对原始决策日期或历史评审过程的还原；备选方案比较是本次整理的工程分析。

## ADR-001：原生 ES 模块与集中兼容接口

**状态：已采用，按当前实现补录。**

### 问题

早期大文件承载多项职责，`MS / QL` 通过原型继承公共对象；页面用手写脚本顺序初始化服务和视图。拆分文件后，如果继续靠全局对象和加载顺序连接，依赖仍然不直观，时间轴与主页面之间还会形成双向调用。

### 当前方案及原因

- 浏览器按原生 `import` 装载具名职责模块，页面各自只有一个模块入口，直接表达依赖并消除手写脚本顺序。
- 页面协调器注入编辑回调，拖拽和编辑器工厂接收上层操作；视图不反向读取主页面的全局方法。
- 保留 `runtime.js / api.js / facade.js` 兼容组合，由入口发布 `window` 接口；内部模块不导入这些门面，避免重新聚成隐式依赖中心。
- 保持运行时零第三方依赖和静态资源发布方式，改动可以逐职责验证，不需要引入新框架来表达当前页面交互。

### 备选方案比较

| 方案 | 优点 | 代价或不适合之处 |
| --- | --- | --- |
| 继续全局脚本并维护顺序清单 | 改动少，兼容原组织方式 | 拆分后的依赖仍隐藏，加载与业务耦合，难以检查独立模块 |
| 原生模块 + 明确页面入口 | 浏览器直接支持静态依赖，维持现有静态发布路径 | 文件请求增多，需要递归预缓存模块图，测试装载方式要适配 |
| 引入框架与打包器重写 | 组件、状态和构建生态成熟 | 当前任务是理清现有边界，全面迁移成本和回归范围显著扩大 |

### 代价和边界

模块内部仍使用可测试的服务对象，而非所有状态都变为不可变数据；兼容对象也仍可读到同一服务状态。这是兼容边界，不是鼓励新业务依赖全局接口。

jsdom 测试装载器只支持项目当前使用的模块语法子集，例如具名导入和导出声明，并显式拒绝循环依赖；它不是完整浏览器模块运行时。新增默认导入、再导出或异步装载等机制时，需要同步调整装载器与静态分析，并以真实浏览器测试验证语义。

未来若模块请求数量或资源缓存成本成为经测量确认的瓶颈，可以在保留职责边界的基础上评估打包；没有必要为了保持此决策永久排除构建工具。

[四个页面入口导航](文件功能说明.md)、[facade.js](../common/js/facade.js)、[modules.js](../tests/helpers/modules.js)、[architecture.test.js](../tests/unit/architecture.test.js)、[静态契约测试](../tests/static/contracts.test.js)。

## ADR-002：稳定存储门面、IndexedDB 事务与共享投影

**状态：已采用，按当前实现补录。**

### 问题

页面需要同步读取本地数据，但 IndexedDB 是异步接口。计时完成可能影响多个日期及并行事件；若先保存任务，再独立写入日记录，中途失败就会出现已完成任务和量化记录不一致。跨标签页的陈旧编辑也可能覆盖其他页刚提交的内容。

### 当前方案及原因

- 使用身份稳定的 `storage.store` 门面，启动时载入内存镜像并切换后端；页面通过就绪入口延后首次读取，领域接口保留同步读取方式。
- 区分乐观镜像和已提交镜像，写入串行排队，事务内对本页基线、提交值与最新磁盘值三方合并。同字段冲突拒绝，确认成功后才推进编辑基线。
- 计时任务与全部受影响日记录在同一事务中提交。`timer-events.js` 提供纯投影，事务层和桥接层分别使用，数据库不依赖桥接内部方法。
- 标签经单一仓库读写，按存储版本失效缓存，读取快照避免跨模块直接改缓存。
- 草稿使用文档所有权和 Web Locks，缺少锁能力时采用明确离页标记；初始化失败进入保护锁定。

### 备选方案比较

| 方案 | 优点 | 代价或不适合之处 |
| --- | --- | --- |
| localStorage 作为唯一后端 | 同步接口简单 | 大容量、事务、多页冲突处理能力有限 |
| 所有领域读取改为异步直读 IDB | 减少完整内存镜像 | 页面和渲染链路需要广泛异步化，仍需解决编辑快照与多键事务 |
| 任务提交后异步补写派生记录 | 保存逻辑表面简单 | 部分失败或页面关闭会留下不一致，不能保证多日整体回滚 |
| 事务内合并和投影 + 同步镜像 | 保留页面读取方式，保证任务与派生记录一致 | 内存有两类镜像，队列、冲突和草稿恢复需要专门测试 |

### 代价和边界

同步受理不等于持久化成功，需要 `flush()` 确认。BroadcastChannel 只负责同源页面通知，不是分布式同步协议。保留单页编辑建议；兼容 localStorage 后端提供尽力回滚，但不宣称具有与 IndexedDB 相同的原子性。

该方案本身保护当前浏览器源内的数据一致性，不提供账户或浏览器清理后的恢复。跨设备传送由 [ADR-003](#adr-003无配对服务的设备直传与确认后整体覆盖) 单独扩展；广播机制仍不能当作分布式同步协议。

### 证据

[数据保障与存储迁移](数据保障与存储迁移.md)、[idb-store.js](../common/js/idb-store.js)、[day-sync.js](../common/js/storage/day-sync.js)、[timer-events.js](../common/js/timer-events.js)、[tag-store.js](../common/js/tag-store.js)、[storage-safety.test.js](../tests/unit/storage-safety.test.js)。

## ADR-003：无配对服务的设备直传与确认后整体覆盖

**状态：已实现于源码；记录日期：2026-11-02。**

### 问题与选择

用户希望省去备份文件的导出、转交和导入，支持手机、平板、电脑之间互传；选择了完全不使用配对服务、双方交换连接码的方式。每次传输由用户指定方向，接收方确认后使用发送方的完整业务快照覆盖，不进行双向自动合并。

采用原生 WebRTC DataChannel。发送端将含完整连接信息的连接码交给接收端，接收端生成应答码交回；两端交换连接信息的机制由应用负责，WebRTC 本身不提供信令服务。[WebRTC 官方建连说明](https://webrtc.org/getting-started/peer-connections)

连接使用 `iceServers: []`，不依赖 STUN/TURN 或公网中继；业务数据经原生加密 DataChannel 发送，使用有序可靠模式、分片和缓冲背压。组包校验值只检测协议处理错误，设备身份依赖用户亲自交换本次连接码，不把它当作账户或永久设备信任。[WebRTC 规范](https://www.w3.org/TR/webrtc/)

### 数据所有权与提交

互传前每个浏览器独立拥有本地数据；本次确认范围内以发送快照为准，目标端独有业务键会删除，范围外的本机设置保留。接收端磁盘数据在预览后变化则要求再次确认；写入、恢复副本、接收回执和新代次一次提交。发送端只以保存回执显示完成。代次保护旧页面和草稿，避免覆盖后再次写入旧内容。

### 代价与边界

- 用户要双向交换较长的连接码；短码或单次扫码的便利需要额外信令机制，本次不引入该依赖。
- 双端保持前台，计时任务先暂停；不提供后台自动同步、多设备同时合并或自动断点续传。
- 同网访客隔离、VPN、防火墙或浏览器候选策略可能阻断直连。浏览器决定候选与路径，代码不以 Wi-Fi 名称验证设备属于同一物理网络。
- 仅支持 IndexedDB 整体覆盖；校验、体积或配额不满足时保留目标数据，不退化为多个独立写入。接收回执丢失时由接收端查看结果。

相较于固定主机保存所有数据，本方案保留各设备独立使用能力；相较于自动双向合并，它减少版本冲突和删除传播规则，代价是用户需要明确选择覆盖方向。

### 证据

[设备快照](../common/js/device-transfer.js)、[直连协议](../common/js/peer-transfer.js)、[整体覆盖事务](../common/js/storage/replace.js)、[数据边界](数据保障与存储迁移.md)、[设备覆盖测试](../tests/unit/device-transfer.test.js)、[真实浏览器测试](../tests/e2e/browser.e2e.js)。

## ADR-004：官方公共服务配对与本机设备记录

**状态：已实现于源码；记录日期：2026-11-02。**

用户希望省去长连接码、二维码相互转交的操作，并避免为其他网站使用者承担自有后台的部署和额度。默认改为 PeerJS 官方共享 PeerServer，保留连接码作为离线及服务故障备用。服务由第三方运营，可访问性和共享容量不能由项目保证；不承诺无互联网配对或跨网直连。[官方公共服务说明](https://peerjs.com/server/cloud)、[PeerJS 连接机制](https://peerjs.com/client/faq)

客户端采用本地固定版本 PeerJS 1.5.5，以具名 ESM 导出替换上游两个浏览器全局导出，保留完整 MIT 许可、原包地址和 SHA-256。这是 ADR-001 零第三方依赖约定的有限例外，不引入前端框架或额外打包步骤。门户 CSP 仅增加官方 `https://0.peerjs.com` 和 `wss://0.peerjs.com` 连接来源，不允许外部脚本。PeerJS 及原数据连接都使用 `iceServers: []`，不采用库的默认 STUN/TURN。[客户端源码](https://github.com/peers/peerjs)

每个本机源使用独立随机 128 位编号 `qlsd-…`。首次添加时额外注册 `qlsp-三位码` 别名，碰撞则明确要求换码。双方在控制 DataChannel 内确认设备名称，并各自持久化随机 256 位共享凭据；双方确认及保存回执完成后才交接业务连接信息。已保存设备重连时校验编号和凭据，PeerServer 编号不作为独立身份证明。忘记设备只删除本机记录，另一端旧记录无法重新通过校验，需要重新添加。[Peer API 的编号用途说明](https://peerjs.com/client/api/peer)

PeerJS 控制连接交换原协议的 offer/answer 长码，然后由原 `peer-transfer` 建立单独业务通道，沿用所有分片、背压、快照校验、确认覆盖及恢复逻辑。代价是建连多一条临时控制通道，优点是业务协议与原子存储不用平行重写。配对完成后断开短码别名的信令注册但保持其控制连接，关闭弹窗销毁全部公共客户端及连接。公共信令断开不主动撤销已经建立的业务通道。

记录单独存于 `qls_paired_devices`（自身 version=1），不升级业务 schema，也不进入业务导出/导入、互传和恢复白名单；清理浏览器数据会丢失身份和配对。页面打开只加载本地客户端，打开互传弹窗且选中设备配对才访问公共服务；同一身份的多个窗口同时注册会报占用，不能静默更换编号破坏已有配对。

证据：[公共配对服务](../common/js/public-pairing.js)、[本机设备记录](../common/js/device-identity.js)、[公共配对界面](../common/js/public-pairing-view.js)、[协议测试](../tests/unit/public-pairing.test.js)、[身份与业务覆盖隔离](../tests/unit/device-identity.test.js)、[真实浏览器官方服务实测](../tests/e2e/browser.e2e.js)。

## 后续记录方式

新决策使用连续 ADR 编号，写明状态、记录日期、具体问题、最终方案、备选方案、代价与验证依据。方案被替代时保留原记录，并链接新的 ADR；不把日常微调都扩写成架构决策。规则变动按[开发规范](开发规范.md)维护，用户可感知或维护相关的已完成变化记入[项目更新日志](项目更新日志.md)。
